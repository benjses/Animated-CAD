    ALIB component libraries

    This page introduces the .alib file format used by Animated-CAD (AniCAD). It explains what these files contain, how AniCAD uses them, how to install or create a library, and what to consider when sharing one.

    What is an .alib file?

    .alib stands for advanced library. An ALIB file is a text-based component library description. It tells AniCAD how to recognise a component imported from a schematic editor, how to draw its symbol, which parameters it has, and how to represent its electrical behaviour in a simulation.

    An ALIB file is not itself a circuit schematic. A schematic contains instances of components and the connections between them; the ALIB library provides the definitions needed to interpret those instances. A single ALIB file can contain multiple component definitions, each enclosed in a <Component> ... </Component> block.

    The format uses XML-like tags, but it is not simply an ordinary XML document. In addition to tags, ALIB supports its own variable substitution, conditional logic, and section-specific conventions. The file is therefore best edited with a text editor and with reference to the examples and rules described below.

    What does AniCAD use an ALIB definition for?

  • Recognition: matches a component type in a schematic file to the appropriate definition.
  • Parameters: declares or interprets values such as resistance, capacitance, model name, source waveform, or other component settings.
  • Symbol and pins: describes the graphical symbol and the names and positions of its electrical connections.
  • Simulation: provides SPICE netlist text, normally for the ngspice simulator, to describe the component's electrical behaviour.
  • Animation: some definitions include an <animation> section that displays values or states calculated during simulation.
  • Help and links: may include a user-facing description, examples, licensing notes, or purchase/datasheet links.
    •

    These parts are related: pin names used in the drawing need to match the connections referenced by the SPICE text. A symbol can look correct and still simulate incorrectly if its pin mapping or model text is wrong.

    How are ALIB files organised?

    The main unit is a <Component> block. The sections inside it are not all mandatory, but a usable definition normally needs at least a schematic declaration and simulation text. Common sections include:

  • <Description> — explanatory text for users and, ideally, licence and model limitations.
  • <qucs_sch> — declaration format for components in Qucs schematics.
  • <eeschema_sch> — declaration format for components in KiCad Eeschema schematics.
  • <Default_Values> — suggested values or parameter strings shown as examples when choosing a component.
  • <qucs_symbol> — drawing instructions for the Qucs-style symbol.
  • <eeschema_symbol> — drawing instructions for a KiCad-style symbol.
  • <Spice> — SPICE/ngspice netlist text used to simulate the component.
  • <animation> — optional instructions for visualising simulated values or component states.
  • <purchase> — optional links, titles and details associated with a component.
    •

    The precise set of sections depends on the component and the schematic editor it supports. For example, some definitions target KiCad only and therefore omit Qucs sections. Some older or specialised definitions may also contain helper sections or named blocks that are used by other parts of the same file.

    For a detailed authoring reference, see Creating components in ALIB files.

    Schematic declarations and component names

    A schematic declaration tells AniCAD which component identifiers in an imported schematic correspond to this definition and how the schematic's fields map to ALIB variables.

    In a Qucs declaration, the first token identifies the component type. The common positional fields include the component name, active state, position, text position, mirroring and rotation; further fields represent component properties. Qucs property values are commonly represented in pairs, such as [value] and [value_v]. The second field in a pair records visibility in Qucs and may be retained for file-format compatibility even if AniCAD does not currently use it.

    In a KiCad Eeschema declaration, the library identifier follows the L marker, and fields such as F 0, F 1, and so on map schematic fields to variables. The exact field layout depends on the KiCad symbol and schematic format. Inspecting a real schematic created by the target editor is often the safest way to establish the correct mapping.

    A component can have declarations for both Qucs and KiCad. It can also have more than one declaration for the same editor when different library symbols use different geometry or field layouts.

    Aliases and multiple declarations

    There are three common ways to reuse a component definition:

  • Support multiple editors: include both Qucs and KiCad schematic sections in the same component.
  • Use ALIAS: after a schematic identifier, an uppercase ALIAS line can list other component identifiers that should use the same definition. This is suitable when the variants share the same symbol geometry, pin positions and electrical model.
  • Use multiple schematic sections: provide separate declarations when variants need different fields, pin coordinates, symbol sizes, or other editor-specific details. This avoids incorrectly treating one variant as geometrically identical to another.
    •

    For example, several logic-gate families may share a common model and pin arrangement and can therefore be aliases. Resistor symbols in different KiCad libraries may have different dimensions and pin positions, so separate declarations can be necessary. See Using one description for multiple component types.

    Symbols and electrical pins

    The symbol section defines the drawing elements and the locations and names of the electrical pins. The format can use AniCAD's default drawing notation or, for KiCad-oriented symbols, a KiCad-style drawing block delimited by DRAW and ENDDRAW.

    In the default notation, drawing elements include lines, rectangles, polygons, ellipses, text and port symbols. A port symbol such as <.PortSym x y [pin_name] angle> defines a named connection at a particular position. In KiCad-style notation, pins are represented by X lines and drawing primitives use KiCad's symbol-library conventions.

    The coordinate systems differ between the two drawing formats: KiCad-style coordinates use a downward-positive Y direction and are generally scaled differently from the default/Qucs-style coordinates. Copying coordinates from one format to the other without adapting them can make the symbol the wrong size or place pins incorrectly.

    For multi-terminal semiconductor devices, the pin captions can be significant to the simulator. For direct ngspice transistor models, use the recognised pin names: MOSFETs use Drain, Gate, Source and Bulk (commonly [D], [G], [S], [B]); BJTs use Collector, Base, Emitter and Substrate (commonly [C], [B], [E], [S]). Case may be accepted, but arbitrary names may not be. Wrapping the device in a subcircuit allows custom external names, at the cost of additional model text.

    SPICE text and simulation behaviour

    The <Spice> section describes how the component participates in the electrical simulation. It usually contains ngspice-compatible netlist lines: passive elements, sources, models, subcircuits, and the instance line that connects the component's pins to the model.

    Variables declared or supplied by the schematic can be inserted into this text. Conditional logic can select different models or construct different netlist fragments depending on a component's value or parameters. This is how one definition can support, for example, several source waveforms, N-channel and P-channel variants, optional series resistance, or different transistor models.

    SPICE syntax and electrical modelling rules still apply. ALIB makes it easier to generate the required text; it does not make an invalid ngspice model valid, nor does it guarantee that a model accurately represents a physical component. Check the model documentation and test important circuits against appropriate reference data.

    For the full component-authoring details, including pin mapping and SPICE examples, see the SPICE section of the creation guide.

    Variables and conditional logic

    One of the main differences between ALIB and simpler component-library formats is that ALIB supports variable declarations and conditional logic. Variables are written in square brackets, for example [name], [value], or a custom name such as [resistance].

    Common predefined variables include the component name, model identifier, position and rotation, the user-entered value, and transient-simulation timing values. Pin names defined in the symbol can also be referenced in the SPICE section.

    A basic definition uses the form DEFINE [variable] value. The format also provides AS_... functions for operations such as changing letter case, extracting or replacing text, parsing numbers, performing calculations, formatting numbers, and setting a parameter's default visibility. Some functions read actual simulation values for animation.

    Conditional blocks use uppercase keywords IF, THEN, optional ELSE, and ENDIF. Conditions can test whether a variable exists, compare text, check whether text starts or ends with a string, match a regular expression, or compare numeric values. This logic can be used in descriptions, drawing sections, SPICE text and other supported areas.

    Variable availability can depend on the section in which it is used. For example, a pin variable may be defined by the drawing section and then be available to the SPICE section, while a schematic-specific property may exist only for one editor's declaration. Test each conditional path and do not assume a variable exists for every schematic format.

    See ALIB variables and ALIB logic statements for the available operations and syntax details.

    Distant connections

    ALIB also supports so-called distant connections. These are additional, usually invisible connections that let one component connect to a pin on another component without drawing a normal wire between them in the schematic.

    This is useful for shared supply connections. For example, a logic IC can obtain its VCC and GND connections from a separate supply component. The library definition declares a named connection with SET_CONNECTION and refers to it from another component with GET_CONNECTION. The resulting local connection can then be included in the component's SPICE instance line like any other pin.

    If a component reports that a distant connection has no source, the circuit may be missing the supply unit or the relevant connection. See Distant connections in ALIB files for both authoring details and a troubleshooting example.

    Animation and displayed simulation values

    Some ALIB definitions include an <animation> section. It can use values calculated during the transient simulation to show the current state of a component or display a measured quantity. For example, a transistor may indicate whether it is off, conducting, or in its linear region; other components can show a current, voltage difference, or an internal model value.

    Pin currents and voltages can be accessed using the animation language's supported expressions. Internal quantities generally need to be saved by the SPICE model first and can then be read by the animation section. These values are evaluated at simulation timesteps when component animation is enabled. A component's animation therefore depends on both a suitable SPICE model and correctly defined animation instructions.

    Animation is an optional presentation layer: it does not replace the underlying circuit model, and a visually informative animation is only as reliable as the simulated quantities from which it is derived.

    How can I add a library to AniCAD?

    The usual method is to copy the .alib file into the libraries directory under the AniCAD installation directory. Some libraries are organised in subdirectories, for example libraries intended specifically for KiCad Eeschema. Keep related files together and follow the directory structure expected by your installation.

    If you are not sure where AniCAD is installed, check the shortcut or the installation directory selected during setup. After adding a library, restart or reload the relevant circuit/library view if AniCAD does not immediately recognise the new components.

    For KiCad symbol libraries, AniCAD also documents a workflow to combine existing ALIB definitions with symbols from .kicad_sym files. This can help add missing symbol drawings while preserving the existing simulation definitions. See Harmonising an internal ALIB library with KiCad symbols.

    How can I create or modify an ALIB file?

    ALIB files are plain text and can be edited in a text editor. The quickest way to learn the format is to start with a similar component in one of the shipped libraries and adapt it carefully. The numbered libraries include basic components, semiconductors, three-phase components, magnetic components, mathematics, flags and measurement components; other files contain specialised or legacy definitions.

    When creating a component, work through the following checks:

    1. Identify the exact component identifier and fields used by the schematic editor.
    2. Define the parameters and provide clear default-value examples where appropriate.
    3. Draw the symbol and verify that every pin has the correct name and position.
    4. Write the SPICE model and ensure its node order matches the symbol's pin mapping and the simulator's requirements.
    5. Add conditional logic only where needed, and test all relevant parameter variants.
    6. If animation is provided, verify that the displayed values correspond to the intended simulated quantities.
    7. Document assumptions, model limitations, sources and licence conditions.
    8. Test the component in a small circuit before relying on it in a larger design.

    Start with Creating components in ALIB files, then consult the focused pages on variables, logic, aliases and multiple declarations, and distant connections.

    Licensing, redistribution and reliability

    There is no single licence that automatically applies to every component in every ALIB file. A library may contain original definitions, adapted models, or SPICE text supplied by a manufacturer or another project. The applicable licence can therefore differ from component to component.

    The AniCAD libraries aim to be as freely usable and redistributable as possible, but some embedded model text may have restrictions on modification or redistribution. Read the component's description and any referenced licence before copying, modifying or publishing it. When creating your own component, include clear information about its source and licence, and preserve notices required by the original licence.

    Component models are provided for their stated purpose and may be simplified, incomplete or inaccurate. They are not guaranteed to be error-free or suitable for safety-critical, production, or compliance decisions. Validate models against datasheets, measurements and the intended operating conditions. If you discover an error in a supplied library, please contact the AniCAD maintainers.
