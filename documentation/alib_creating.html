    The following text is for developers, who want to write new ".alib"-files or want to add Components to existing ones. If you have general questions about the ".alib"-files, then check out the overview about alib-libraries

    How to create Components in ".alib"-files

    Sections of the ".alib"-file

    A component in ".alib"-files has the following sections: (example here, open with text editor)
  • Description : Some informations for the user
  • Schematic : Declares the component and its variables
  • Symbol : Describes the connections and the drawing elements of the component
  • Spicetext : Describes how the component shall be simulated in Ngspice
    •
    The Symbol and the Spicetext sections support logic statements,
    also, it supports connecting to the pins of other components with distant connections

    Description

    The Description is optional, however we recommend to describe each component properly. Also the description should contain some license information.

    Schematic

    The Schematic is mandatory, since it is needed to describe and to identify the component. Also the Schematic contains the variables, for example the ohmic value of a resistor.
    There may be a Schematic section for Q.U.C.S. and / or for KiCad Eeschema. The Schematic sections for these schematic creation programs are different since they are adapted to the schematic files (".sch"-files) format of each program. To see how these sections are adapted to the schematic format of Q.U.C.S or of Eeschema, you can compare these schematic files to Example 1 below:

    The schematic sections may contain ALIAS lines. This is a line that starts with the word "ALIAS " (written in uppercase, without the apostrophes). After this buzzword, you can list up all the names this component may have - see in Example 2, below. Also, you may write multiple schematic sections in one component, see in the description of how to use a component description multiple times
    As in qucs-schematics, the identification of the component is the first word of that section, which in Example 1 is R
    The variables in qucs are simply listed one after another, separated by a space: after the identifier, there are always the same eight variables which are:
    [name] [active] [xpos] [ypos] [xtext] [ytext] [mirrorx] [rotate] , and after that there usually are some additional variables, for example [value] and [value_v].
    The easiest way to find out which additional variables a component needs, is to open that component in Q.U.C.S and check out the Dialog "Edit Component Properties" (see this screenshot made from Q.U.C.S. component showing the properties of a Resistor). You need a pair of additional variables for each property listed in that dialog, for example [X] and [X_v]. Because the second one of this pair, the one with the additional "_v", is a boolean value which states whether the first one of this pair is visible in Q.U.C.S. (however it is not relevant for AniCAD at the moment. Still needed for compatibility)

    As in Eeschema-schematics, the identification of the component is the word after the L, which is in Example 1 pspice:R.
    The variables are listed with identifiers "F 0","F 1","F 2"... and for each variable/identifier, a new line is needed. Here you can find out in a similar way, to open the component in eeschema, and writing down the variables stated in the dialog window. However, to find out the format of text you can easily look up the text in a schematic file which was created with eeschema. There you may find text similar to this one: (The parts in strikethrough are not needed for the library. The parts marked in blue are the variables' parameters and need to be replaced by the variable:
    $Comp
    L pspice:R R2
    U 1 1 5D46EFFA
    P 2400 2150
    F 0 "R2" V 2195 2150 50 0000 C CNN
    F 1 "10" V 2286 2150 50 0000 C CNN
    F 2 "" H 2400 2150 50 0001 C CNN
    F 3 "~" H 2400 2150 50 0001 C CNN
    1 2400 2150
    -1 0 0 1
    $EndComp

    Symbol

    The Symbol is mandatory for qucs, and is optional for Eeschema. That is because usually eeschema creates a "cache.lib"-file for each schematic in the same directory and that "cache.lib" file contains drawing information for each component of the schematic. However, in most cases it is better to create a Symbol section for Eeschema, because first, you can individualize the drawing, second the "cache.lib" file can get lost and third and most important, you can control the names and positions of the connections of the component if you specify a symbol.
    The symbol section may be written in one of two available formats, which will be called default-format and eeschema-format:
    We made the eeschema-format available so that you can easily implement your own adaptions to eeschema drawings. Under this external link, is a documentation "LibraryFileFormats.pdf" for KiCad, which contains a section called "Drawing section", where the drawing elements of the eeschema-format are explained, too. The default-format is an XML-style drawing description, and the eeschema-format has one drawing element per line. The default-format can be used for all kinds of Symbol sections, the eeschema-format can only be used for eeschema_sch sections.

    If you want to use the eeschema-format, you need to start your Symbol section with the line DRAW and end that section with the line ENDDRAW, as shown in Example 1 below.
    Otherwise the default-format is used.

    In eeschema-format, the filling of a rectangle, polygon, circle or arc is determined by the variable "cc": If that variable's value is F, then it is filled; if it is N then it is not filled. In default format, the variable "filled" determines the filling of the form; if it is "1" then it is filled, if it is "0" then it is not filled.

    For ports, "caption" and "name" both are the identifier for that port. But "caption" in default-format needs the brackets "[" and "]", whereas the "name" in eeschema-format shall not have the brackets.
    Also, the port-name in eeschema-format is printed on the schematic automatically, whereas the port-caption is not.

    Note that the y-coordinates in eeschema-format are negative in that table. That is because the coordinate system in eeschema-format is adapted to the coordinate system for declaration of components in KiCad Eeschema, where the positive Y-Direction is Downwards, whereas in default-format the positive Y-Direction is upwards.
    Also the coordinate numbers are 10 times larger in eeschema-format, because a circuit with the same coordinates would be drawn about ten times smaller in KiCad-Eeschema than in Q.U.C.S.

    The default-format supports logic statements

    Spicetext

    The spicetext is mandatory, since it is needed to describe the component's electric caracteristic. Generally the spicetext-section contains the netlist information for NGSpice, which is described in detail in this very detailed Ngspice user manual

    The spice section supports logic statements. In the spice section you should also use the variables which were declared in the Schematic section above. Also you should use the connections' identifiers which were declared in the symbol section above.

    Please be aware that components with more than two connections, such as Transistors need specific names, in order to be simulated correctly by ngspice. These specific names are the same as the ones which are used in ngspice.
    -> for MOSFETs, the Drain Gate Source and Bulk connections must use the captions [D] [G] [S] and [B], lower case is also acceptable, but no other caption.
    -> for BJTs, the Collector Base Emitter and Substrate connections must use the captions [C] [B] [E] and [S], lower case is also acceptable, but no other caption.

    If you are not aware about the correct names, you may search in the Ngspice user manual, or you can put your device into a subcircuit. In case of subcircuit, you can give out names of connections as you like and the currents through that pin are still simulated. But this option is a bit more to write and a bit slower than directly using the correct pin names.

    Example 1

    A component may be described like this example:
    (This example describes a resistor. It is a shortened version of the resistor from the components.alib file in the standard library)
    <Component> // start of component

      <Description> // start of description section
       Example component, resistor. // Information about component itself
       This component is public domain. // Information about license
      </Description> // end of description section

      <qucs_sch> // start of Schematic for Q.U.C.S.
        R [name] [active] [xpos] [ypos] [xtext] [ytext] [mirrorx] [rotate] [value] [value_v] ... // declaration of that component, but shortened, for schematics in Q.U.C.S.
        // qucs-identificator of this component is R, because that declaration's first word is R
      </qucs_sch> // end of Schematic for Q.U.C.S.

      <qucs_symbol> // start of Symbol for Q.U.C.S.
       <Rectangle -18 -9 36 18 #000080 2 1 #000080 1 0> // Drawing of a rectangle with starting point (-18 | -9), dx=36, dy=18, so ending point is (18 | 9)
       <.PortSym -30 0 [pin1] 0> // first connection at (-30 | 0). Here we give it the name "pin1"
       <.PortSym 30 0 [pin2] 0> // second connection at (30 | 0). Here we give it the name "pin2"
       <Line -30 0 12 0 #000080 2 1> // drawing of a line beween the rectangle and "pin1"
       <Line 30 0 -12 0 #000080 2 1> // drawing of a line beween the rectangle and "pin2"
      </qucs_symbol> // end of Symbol for Q.U.C.S.

      <eeschema_sch> // start of Schematic for KiCad Eeschema
        L pspice:R // eeschema-identificator of this component is pspice:R , because that is what is followed by the L
        F 0 "[name]" // identification of variable [name] to the line starting with F 0
        F 1 "[value]" // identification of variable [value] to the line starting with F 1
        F 2 "[footprint]" // identification of variable [footprint] to the line starting with F 2
        F 3 "[datasheet]" // identification of variable [datasheet] to the line starting with F 3
        // F0 to F3 are nearly always the same. Therefor these are set by default, and can be omitted as in Example 2 below.
      </eeschema_sch> // end of Schematic for Eeschema

      <eeschema_symbol> // start of Symbol for Eeschema
        DRAW // start marker for EESCHEMA-style drawing notation
        S -40 150 40 -150 0 1 0 N // drawing of a rectangle with starting point (-40 | 150) and ending point (40 | -150)
        X ~ 1 0 250 100 D 50 50 1 1 P // first connection at (0 | 250). Includes a connection line with length 100 Downwards to the rectangle.
        X ~ 2 0 -250 100 U 50 50 1 1 P // second connection at (0 | -250). Includes a connection line with length 100 Upwards to the rectangle.
       // The name of these connections are not specified expicitely but just marked as empty by a "~".
       // In these cases, the names of the connections are automatically created by AniCAD to start with "pin" and end with the connection number.
       // Here that is "pin1" and "pin2",
    //That is also why the pins in the Symbol for Q.U.C.S were given the same names: So that these two pinnames can be used in the spice section below
        ENDDRAW // end marker for EESCHEMA-style drawing notation
      </eeschema_symbol> // end of Symbol for Eeschema

      <Spice> // start of description section
       R_[name] [pin1] [pin2] [value] // Spice simulation line of the component.
       // Uses the name and the value declared in the schematic and the connections declared in the symbol
      </Spice> // end of description section

    </Component> // end of component

    definitions

    The AniCAD allows definitions of constants in seperate lines, which have the form:
    DEFINE [cname] K1 //defines the constant [cname] to the value K1
    the definitions can be used in:
  • The declaration, see above
  • The drawing section, see above
  • The spice section, see above and
  • The parameter-definitions-section,called "param"-section", which has the sole purpose to define constant parameters:

    Example 2

    The following example shows the use of define-lines
    Define-lines are also intensively used in the library for relays), but let's start with this example:
    <Component>
      <eeschema_sch>
        DEFINE [producer] A//Definitions for the three components below
        L Relay:ProducerA_ModelA5_5V
        L Relay:ProducerA_ModelA12_12V
        L Relay:ProducerA_ModelAERR_error
      </eeschema_sch>
    // there can be multiple definitions sections:
      <eeschema_sch>
        L Relay:ProducerB_ModelA5_5V
        L Relay:ProducerB_ModelA12_12V
        DEFINE [producer] B//Definitions for the two components above
      </eeschema_sch>

      <param>
        IF [model] ENDS_WITH 5V THEN
         DEFINE [nominal_voltage] 5
        ELSEIF [model] ENDS_WITH 12V THEN
         DEFINE [nominal_voltage] 12
        ELSE<ERROR>Unknown nominal voltage</ERROR> // gives out an error message if the component is of model ProducerA_ModelAERR_error
        END END // Close the two IF-Statements
      </param>

      <eeschema_symbol>
        DRAW
        IF [producer] EQUAL_TO A THEN
        //drawing of the component in the same style as producer A does in his datasheet
        ELSEIF [producer] EQUAL_TO B THEN
        //drawing of the component in the same style as producer B does in his datasheet
        ENDEND // Close the two IF-Statements
        ENDDRAW
      </eeschema_symbol>

      <Spice>
        IF [nominal_voltage] EQUAL_OR_HIGHER_THAN 12 THEN
        //some model for relays with nominal voltage U_n>=12V
        ELSEIF [nominal_voltage] LOWER_THAN 5 THEN
        //some model for relays with U_n<5V
        ELSE
        //some model for relays with U_n between 5V and 12V
        ENDEND
      </Spice>

    </Component>
